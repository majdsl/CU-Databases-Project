# InnoDB cache pressure: table size versus buffer pool

Status: implementation prepared; laptop pilot/full measurements and findings are pending.
This is a targeted InnoDB mechanism experiment, not a five-engine larger-data ranking.

## Question and scope

What happens to random lookup latency and InnoDB read activity when the table is
larger than a fixed buffer pool? The earlier warm flight tables did not establish
this behavior. Here, two table sizes share the same schema, generation rule and
128 MiB InnoDB buffer pool. Actual engine-reported table bytes are checked, and
read counters are recorded alongside verified timings.

This does not equalize caches across different engines. Table size also changes
B-tree size/height and access locality, so a timing difference alone is not a pure
causal estimate of the buffer-pool effect. Inspect the counters and plans. A further
same-table/different-pool experiment would be needed to isolate pool capacity more
closely. No claim of physical SSD latency or data exceeding host RAM is made.

## Schema and data

```sql
CREATE TABLE cache_pressure_rows (
  id INT NOT NULL PRIMARY KEY,
  payload VARBINARY(1024) NOT NULL
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC;
```

The integer key supports random point reads and ordered full verification. Each
payload contains 1,024 deterministic SHAKE-256 bytes derived from seed 20261017 and
the key. This avoids repeated text padding and collation overhead. No compressed
row format or secondary index is used. Small-table rows are an exact prefix of the
large dataset. These are diagnostic bytes, not flight records.

- Small: 32,768 rows, 32 MiB payload. The actual table allocation must be below 128 MiB.
- Large: 262,144 rows, 256 MiB payload before row/index overhead. Actual table allocation
  must exceed the 128 MiB pool. Payload alone is twice the configured pool.
- The server pool size is read before and after queries; a mismatch aborts the trial.
  Startup fixes its size, maximum and automatic-shrink minimum to 128 MiB. Pool dump/load
  is disabled. Table metadata is an engine estimate, not filesystem or physical SSD usage.

Data generation and loading use batches of 500; full validation uses an unbuffered
cursor and batches of 500. The runner does not hold a 256 MiB result set in memory.
Every loaded byte is compared to the deterministic expected payload, and an ordered
SHA-256 digest is independently regenerated by the host. CRC32 sums provide a separate
full-scan oracle; CRC32 alone is not used as the integrity guarantee.

## Isolation, schedule and timings

The host script creates a new UUID-named Compose project and a fresh named volume
for **each** trial. The normal lab database is not resized, stopped or deleted.
There is no exposed database port. The benchmark account remains scoped to engine_lab;
credentials come from the existing private .env. Do not upload that file.

Pilot: two trials, one per size. Full: six rounds per size (12 trials), alternating
small/large order so each size runs first three times. Fresh volumes remove prior
trial database state, but do not clear OS or virtualization caches.

1. Build/start the isolated stack and verify its container/project/volume identity.
2. Verify actual InnoDB engine, fixed pool size and absent target table.
3. Load data, stream-verify every row, and run ANALYZE. Verify actual table allocation.
4. Run 1,000 seeded warmup point queries. Then time 1,000 pilot or 5,000 full point
   queries with uniformly sampled keys (with replacement). Each fetch returns the full
   payload, checked outside the measured interval. Record query IDs and every timing.
5. Run three full scans: COUNT(*) and SUM(CRC32(payload)). Each answer must match the
   host-checked row count and CRC oracle. Record every scan time and counter window.
6. Record EXPLAIN, table status, settings, runtime and image/source identities. Stop
   cleanly and remove only the successfully validated isolated project's resources.

Random lookups follow full verification and explicit warmup. Scans follow random
lookups, with no separate scan warmup. This is a fixed phase order, not a cold-cache
or fully steady-state protocol. The load timer includes Python payload generation
and insertion; it is not server-only ingest throughput. Scan cost includes CRC32
computation, so it is not directly comparable with the earlier aggregate benchmarks.

Statistics use six trial means per size, with mean and sample SD. Individual queries
are not independent trial replicates. All raw samples remain available. Pilot evidence
stays separate. No full conclusions should be drawn before examining its counter data.

## Counters and interpretation

The following GLOBAL InnoDB counters are read before/after the entire point-query
phase and each scan: Innodb_buffer_pool_reads, Innodb_buffer_pool_read_requests,
Innodb_buffer_pool_read_ahead, Innodb_buffer_pool_wait_free, Innodb_data_reads and
Innodb_data_read. Dirty/data/free page gauges are recorded as snapshots, not monotonic
counters. Missing counters or decreasing cumulative counters abort the trial.

Buffer-pool reads indicate reads that were not satisfied from that pool; data-read
bytes and read-ahead help interpret their scope. They do not prove access to physical
SSD media: the OS, Docker VM and storage layer may serve those requests from cache.
These are server-global windows, not exact attribution to one SQL statement. A fresh
isolated server reduces unrelated SQL, but healthchecks and background flushing can
still contribute. Dirty pages before/after expose some of that background state;
we do not force a checkpoint or require all dirty pages to drain before timing.

Counters surround a phase, including client-side validation/generation between queries.
Timing samples surround execute/fetch only. Driver/network and scheduling are included;
server CPU, lock waits and client overhead are not separated. This is a single-client
experiment on one host, not concurrency evidence or a general engine ranking.

## Running on the laptop

Use the existing checkout and .env, Docker Linux amd64 and local Python 3.9+.
Allow several GiB of free Docker storage plus the existing images. A large trial
writes hundreds of MiB; the full run rebuilds both tables six times. Duration depends
on the machine. Do not run other benchmarks or heavy applications concurrently.
The database limit is 2 CPUs/2 GiB; the runner is 1 CPU/512 MiB.

Stop the normal lab before measuring so it does not compete for resources:

```powershell
docker compose stop
python scripts/run_cache_pressure.py --pilot --power-condition "plugged in; battery saver off"
```

The host script builds the isolated images itself. Use your actual power label.
Review results.json, actual allocation and read counters before proceeding:

```powershell
python scripts/run_cache_pressure.py --full --power-condition "plugged in; battery saver off"
```

Results are written by host Python under results/<run-id>, avoiding runner bind-mount
permission issues. trial-NN.json preserves each worker result; results.json adds host
validation, image IDs and clean-stop records. On failure, partial results and the failed
project/volume are retained, with best-effort database stop and diagnostic log capture.
Inspect the exact named project before retrying. Do not manually delete normal lab data.
The ordinary lab can later be restarted with docker compose up -d --wait db.

## Correctness checks

Unit tests cover streaming verification, corrupt/missing/extra rows, known data oracles,
size/order checks, fixed pool/actual footprint, counter resets/missing values, isolation,
pre-existing resources, unclean shutdown and failure retention. CI runs the entire host
orchestrator with --smoke: 128/1,024 rows, 30 queries, 10 warmups and two scans per trial.
That smoke verifies real SQL, fresh-volume lifecycle and reporting, but deliberately
skips large-footprint thresholds. It cannot validate cache-pressure results; the laptop
pilot must do that. No smoke timing is benchmark evidence.
